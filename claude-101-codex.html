Codex en VS Code

Cómo instalar y usar el agente de código de OpenAI: la extensión de VS Code, la misma herramienta en la terminal, y qué cambia respecto a lo que vimos en clase con Claude Code.

Volver a la clase

En la sesión trabajamos con Claude Code, que vive en la terminal. Codex es la respuesta de OpenAI a lo mismo: un agente que lee tu repositorio, propone cambios en varios archivos, corre comandos y te muestra un diff para que apruebes. Lo interesante para ustedes es que trae extensión oficial de VS Code, así que no tienes que salir del editor.

El flujo de trabajo es idéntico al de la clase: das contexto, pides un cambio concreto, lees el diff, apruebas o corriges. Si eso ya lo entendiste, cambiar de herramienta es cuestión de veinte minutos.

Codex es la misma disciplina de la clase con otro modelo debajo. Lo que no cambia es que el diff lo revisas tú.

Qué es y en qué formas viene

FormaDónde vivePara qué
Extensión de IDE VS Code, y la misma extensión sirve en Cursor y Windsurf. JetBrains y Xcode tienen integración propia. Panel al lado del código: chat, diffs y aplicar cambios sin cambiar de ventana. Es la que recomiendo para el proyecto.
CLI Terminal (macOS, Linux, Windows) Sesiones agénticas largas, ejecución no interactiva y scripts. Es el equivalente directo a Claude Code.
Codex en la web Navegador, con tu cuenta de ChatGPT Delegar tareas grandes a la nube y volver por el resultado. Desde el IDE puedes escalar un chat a la web y seguir el mismo hilo.

Qué necesitas antes de empezar

  • Una cuenta de ChatGPT. El inicio de sesión es con esa cuenta, no con una API key, y el uso se descuenta de tu plan.
  • Un plan que incluya Codex. Está en Go, Plus, Pro, Business, Edu y Enterprise. El plan gratuito solo deja probar tareas cortas, y la extensión de VS Code pide plan pago: con cuenta Free no arranca.
  • O una API key, si prefieres pagar por token en lugar de por plan. Sirve en la CLI y no depende de la suscripción.
  • Git. No es obligatorio, pero sin control de versiones no tienes cómo devolver un cambio que salió mal. Eso aplica a cualquier agente.

Antes de pagar

Si no tienes plan pago de ChatGPT, no compres uno para esta clase. Revisa primero Sin suscripción: con GitHub Education, Copilot o un agente libre conectado a una capa gratuita haces el proyecto completo sin gastar nada.

Instalarlo en VS Code

  1. Instala la extensión

    En VS Code abre el panel de extensiones (Cmd/Ctrl + Shift + X) y busca Codex. La oficial la publica OpenAI y su identificador es openai.chatgpt; confirma eso antes de instalar, porque hay clones con nombres parecidos.

    Si prefieres no buscar, abre Quick Open con Cmd/Ctrl + P y pega:

    ext install openai.chatgpt

  2. Abre el panel e inicia sesión

    Haz clic en el icono de Codex en la barra lateral. Si no aparece, abre la paleta de comandos (Cmd/Ctrl + Shift + P) y corre Codex: Open Codex Sidebar. Te va a pedir iniciar sesión con ChatGPT: se abre el navegador, autorizas y vuelves al editor.

  3. Abre la carpeta del proyecto, no un archivo suelto

    Codex razona sobre el repositorio completo. Si abres un solo archivo pierde la mitad del contexto y responde peor.

  4. Fija los permisos antes del primer prompt

    Decide desde el principio si puede editar archivos y correr comandos solo, o si te pregunta cada vez. Para explorar un repo que no conoces, arranca en modo de solo lectura.

  5. Escribe el archivo de instrucciones del repo

    Es el AGENTS.md, el equivalente del CLAUDE.md que leyeron en campusflow-api. Más abajo está qué poner.

Cómo se trabaja en el editor

Contexto desde el editor

Puedes referenciar archivos abiertos y el código que tengas seleccionado directamente en el cuadro de texto, sin volver a pegarlo. También puedes adjuntar chats recientes para no repetir lo que ya explicaste.

Revisión de cambios

Los cambios llegan como diff al lado del archivo, con la explicación de por qué los hizo. Los aplicas o los rechazas ahí mismo, uno por uno.

Delegar a la nube

Si la tarea es grande, la escalas a Codex web sin perder el hilo de la conversación, y vuelves al editor cuando hay algo que revisar.

Aprobaciones

El nivel de permiso se cambia desde el panel. Es lo primero que hay que ajustar y lo último que hay que aflojar.

Un primer prompt que sirve para arrancar en cualquier repo:

Prompt de entrada a un repositorio

Antes de cambiar nada: lee el repositorio y explícame en máximo
diez líneas qué hace, cómo se corre y dónde está la lógica de negocio.
Dime también qué NO entendiste todavía.
No edites ningún archivo en este turno.

Ese "no edites nada en este turno" es la costumbre que más les va a servir. Un agente con permiso de escritura y un prompt vago hace veinte cambios que después nadie quiere revisar.

Instalarlo en la terminal

La CLI es la misma herramienta sin el editor alrededor. Si les gustó cómo se sentía Claude Code en la demo, esta es la comparación justa. Escoge una sola forma de instalar.

macOS y Linux

curl -fsSL https://chatgpt.com/codex/install.sh | sh

Con Homebrew: brew install --cask codex

Windows · PowerShell

powershell -ExecutionPolicy ByPass -c "irm https://chatgpt.com/codex/install.ps1 | iex"

En Windows conviene trabajar dentro de WSL si el proyecto usa herramientas de Linux.

Con Node ya instalado

npm install -g @openai/codex

También hay binarios en las releases del repositorio openai/codex en GitHub.

Primera sesión

cd tu-proyecto
codex

Al arrancar te ofrece iniciar sesión con ChatGPT. Autorizas en el navegador y quedas listo. La configuración vive en ~/.codex/config.toml.

Permisos: los tres perfiles

Codex separa dos cosas que conviene no confundir. El sandbox define qué puede hacer técnicamente cuando ejecuta un comando; la política de aprobación define cuándo tiene que preguntarte. Los perfiles que vienen de fábrica son tres.

PerfilQué permiteCuándo usarlo
:read-onlyEjecución local en modo solo lecturaEntender un repo, planear, revisar. Empieza aquí.
:workspaceEscribe dentro del proyecto y en los temporales del sistemaEl modo de trabajo normal
:danger-full-accessQuita las restricciones del sandbox localCasi nunca, y solo si entiendes exactamente por qué lo necesitas

En la sesión lo cambias con /permissions. Para dejarlo fijo, en ~/.codex/config.toml:

default_permissions = ":read-only"

Cuidado

Los perfiles de permisos y los ajustes viejos de sandbox no se combinan. Configura default_permissions con su bloque [permissions], o los sandbox_mode antiguos, pero no los dos: si mezclas, no vas a saber qué está mandando.

AGENTS.md, el archivo que cambia todo

Es el mismo truco del CLAUDE.md: un archivo en la raíz del repositorio con las reglas de la casa, que el agente lee antes de responder. Con él, el primer prompt ya sale bien; sin él, pasas tres turnos corrigiendo cosas que ya sabías.

/init te escribe un borrador leyendo el proyecto. Revísalo y agrégale lo que un agente no puede adivinar:

Qué poner en AGENTS.md

# AGENTS.md

## El proyecto
Qué es, para quién, y qué NO es.

## Cómo se corre
Comandos exactos: instalar, migrar, sembrar datos, correr, probar.

## Estructura
Qué hay en cada carpeta y dónde vive la lógica de negocio.

## Reglas del código
Estilo, nombres, manejo de errores, qué librerías están permitidas
y cuáles están prohibidas y por qué.

## Antes de terminar
Corre las pruebas. No toques migraciones sin avisar.
Nada de credenciales en el código.

Escríbelo en el idioma en que trabaja el equipo y mantenlo corto. Un AGENTS.md de tres páginas que nadie actualiza es peor que media página que sí refleja el proyecto.

Pruébalo con el repo de la clase

El mismo ejercicio que hicimos con Claude Code sirve para comparar. En claude-101/campusflow-api hay un bug intencional y una feature sin implementar.

cd claude-101/campusflow-api
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python seed.py
codex

1 · El bug

En modo :read-only, pídele que revise el campo status que devuelve GET /courses/1/agenda para la entrega que vence hoy a las 23:59, y que te explique la causa antes de proponer el arreglo.

2 · La feature

GET /courses/1/workload responde 501. Pasa a :workspace, pídele la implementación con pruebas, y revisa el diff línea por línea antes de aplicarlo.

Cuando termines, la pregunta interesante no es cuál de los dos agentes acertó, sino en qué se equivocaron distinto. Eso es lo que van a contar en la sustentación.

La conclusión aburrida es la correcta: se parecen mucho más de lo que se diferencian. Los conceptos de la clase —contexto, especificación, revisión del diff, responsabilidad sobre el resultado— se transfieren enteros. Aprende uno bien y el otro te toma una tarde.

Antes de soltarlo en tu proyecto

  • La cuota se mide en mensajes por ventanas de cinco horas y varía según el modelo. Un agente hace muchas llamadas por tarea, así que se acaba antes de lo que uno cree. Ten tu plan B configurado y no dejes la entrega para la última noche.
  • Revisa el diff completo. Que el código corra no significa que esté bien. Sigue aplicando el criterio de la sección de buenas prácticas: leer, entender, y solo entonces aprobar.
  • No le des acceso total por comodidad. :danger-full-access quita el sandbox: un comando mal generado ahí ya no tiene red de protección.
  • Cuida qué mandas. Datos de otras personas, credenciales y material confidencial no se le pasan a ningún agente, ni de OpenAI ni de nadie.
  • Deja rastro. Para la evidencia de uso de IA del proyecto, guarda los prompts y qué aceptaste o rechazaste de cada respuesta. Vale igual con Codex que con Claude.

Para ingenieros

codex exec no abre sesión interactiva, así que se puede meter en un hook de git o en CI: por ejemplo, una revisión automática del diff antes de abrir el pull request. Es útil, pero decide primero qué pasa cuando el agente se equivoca en ese punto de la cadena.

La herramienta cambia cada seis meses. La responsabilidad sobre lo que entregas, no.
